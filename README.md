# NMシリーズ保守 RAG課題

「NMシリーズ 保守技術ガイド」「NMシリーズ 運用記録・サービス速報」の2資料を対象に、
自然言語の質問に対して資料名・ページ番号付きで回答するRAGシステム。

## 0. セットアップ

```bash
pip install -r requirements.txt
cp .env.example .env
# .env に OPENAI_API_KEY を設定する
```

`data/` に以下2ファイルを配置済み:
- `01_NMシリーズ保守技術ガイド.pdf`
- `02_NMシリーズ運用記録サービス速報.pdf`

## 1. 実行方法

```bash
# 1) 取り込み(チャンク化 -> Embedding -> Chroma保存)
python ingest.py

# 2) 質問(対話モード)
python rag.py
# もしくは単発質問
python rag.py "R-104でE-204が再発した場合どうすればいい？"

# 3) 評価(設計書の10問を実行し eval_report.md を出力)
python evaluate.py
```

`.env` の `EMBEDDING_BACKEND` / `LLM_BACKEND` を `local` にすると、
OpenAI APIキーが無くてもTF-IDFベースの簡易Embeddingとテキスト抽出のみの
スタブLLMでパイプライン全体の配線(検索・出典表示・判断不能処理)を確認できる。
**本番の回答精度評価は必ず `openai` バックエンドで行うこと**（`local`は配線確認専用で
回答の自然文生成は行わず、精度の参考にはならない）。

## 2. 設計方針

### 2.1 チャンク設計 (`chunker.py`)

- 単純な文字数分割ではなく、**表は1表=1チャンク**、**本文は見出し単位で1セクション=1チャンク**とした。
- 表の検出はPyMuPDFの`find_tables()`を使用。ただし罫線のない表で**右端カラムが検出漏れする問題を実データで確認**したため
  (「交換部品と互換条件」表の「状態」列が欠落する)、表の右端より右側にある単語を行のy座標帯で走査し、
  列を自動補修する`repair_table()`を実装した。
- 本文は「1.1 機種と主要構成」「3.1 E-204 左駆動系過負荷」「サービス速報 SB-2026-014」のような
  番号付き見出し/固有パターンでセクション分割し、短い断片は前後と統合する。
- 各ページの冒頭に繰り返される資料名(ランニングヘッダ)やページ番号(「3 / 5」)は本文から除去し、
  かつこれを除去しないと資料名の一部の文字列(「サービス速報」)がdocument_type分類を誤動作させる
  バグにつながることも実際に確認・修正した。

### 2.2 メタデータ設計

各チャンクに正規表現で以下を抽出して付与する:

| フィールド | 例 | 用途 |
|---|---|---|
| document / page | NMシリーズ 保守技術ガイド / p.2 | 出典表示に必須 |
| document_type | maintenance_guide / service_bulletin / asset_ledger / case_history | 優先順位判定 |
| model | NM-100S | 機種フィルタ |
| machine_id | R-104 | 個体フィルタ |
| lot | L2408 | ロット条件判定 |
| firmware | 3.1.4 | FW条件判定 |
| error_code | E-204 | 症状検索 |
| part_number | DRV-42A | 部品互換判定 |
| bulletin_id | SB-2026-014 | 速報特定 |
| case_id | CASE-017 | 事例特定 |
| priority | 3(速報) > 2(一般手順/台帳) > 1(事例) | 優先順位付け |

`document_type`は運用記録PDF内でも本文の内容(サービス速報本文か、事例集か、機器台帳か)に応じて
`refine_document_type()`で再分類しており、単一PDF=単一document_typeにはしていない。

### 2.3 検索(Retriever)設計 (`rag.py`)

1. 質問文をEmbeddingしてChromaでベクトル類似度検索(top_k)。
2. **質問文自体にも同じ正規表現でmachine_id/error_code/bulletin_id等を抽出**し、
   それに完全一致するチャンクをmetadata filterで追加取得する。
   「R-104でE-204が再発したら」のような複合質問は、類似度検索だけでは保守ガイド・運用記録・
   サービス速報の3資料を拾いきれないことがあるため、このハイブリッド検索を採用した。
3. 取得したチャンクは `priority`(document_type優先度)を第一キー、類似度スコアを第二キーとして
   並べ替えてからLLMへ渡す。これにより「対象条件に一致するサービス速報を一般手順より優先する」
   という資料内ルールを、検索結果の提示順の面からも担保している。

### 2.4 回答生成・「判断不能」処理

プロンプトで以下を明示している(`rag.py` の `SYSTEM_PROMPT`):
- 提供チャンクのみを根拠にし、推測しない
- 複数資料の組み合わせを許可する
- service_bulletin > maintenance_guide/asset_ledger > case_history の優先順位に従う
- 判断できない場合は「提供された資料からは判断できません」と回答する
- 出典を「資料名 p.ページ番号」形式で必ず列挙する

## 3. 評価

`evaluate.py` は設計書記載の10問を実行し、各質問について
「狙ったdocument_type・メタデータのチャンクを検索で拾えているか」を自動チェックしたうえで、
LLMの実際の回答とあわせて `eval_report.md` に出力する。

同梱の `eval_report.md` は `local`(TF-IDF+スタブLLM)バックエンドでの**配線確認用サンプル実行結果**であり、
検索精度チェックは10問中9問がOK(Q2のみ、TF-IDFの表現力不足により取りこぼし)。
OpenAI Embeddings + GPT系モデルで再実行すれば、より高い検索精度・自然な回答文が得られる想定。
本番評価は `OPENAI_API_KEY` を設定した上で `python evaluate.py` を再実行して行うこと。

## 4. 既知の制約・今後の改善余地

- 表の列補修(`repair_table`)は「右端カラムの欠落」に特化した対処であり、複雑な結合セルや
  縦方向の欠落には未対応。
- ロット・FWの「範囲」条件(例: L2406〜L2410にR-104のL2408が含まれるか)は、現状メタデータの
  完全一致/部分一致でしか判定していない。範囲を数値として解釈した厳密な包含判定は未実装。
- `local`バックエンド(TF-IDF)は配線検証用であり、実運用の検索精度はOpenAI Embeddingsでの
  評価結果を正とすること。
